### 5.2 每日建议台账：胜 / 负与累计 ROI

**问题**：每天给出去的建议，整体是赚还是亏？此前这个问题没有答案 —— 逐日复盘散落在会话记录里，
既不能累计，也无法回答「这套方法长期有效吗」。

**台账文件** `scripts/data/rec_pnl_log.csv`（**已纳入 git**，与 `.gitignore` 掉的 `decision_log.csv` 不同）。
一条腿一行；以 `#` 开头的行是口径说明，脚本会跳过。

| 字段 | 含义 |
|---|---|
| `settle_date` | 结算日（= 目标日） |
| `leg` / `side` / `bucket` | 腿名 / `YES`·`NO` / 档位 N（`N°C = [N.0, N+1.0)`） |
| `entry_price` | **首推可执行价** |
| `cost_usd` | 建议投入（USDC）；份数由 `cost ÷ price` 反推 |
| `settle_bucket` / `settle_status` | 实际结算档 / `confirmed`·`provisional` |
| `outcome` | `win` / `loss` / `open` |
| `note` | 一句话事后归因 |

**计入口径（重要，防止自我美化）**
1. **每条腿只记一次**：取「**首推价 + 建议仓位数**」。同一条腿后续的加仓、改价一律不重复计入
   —— 否则同一论点被反复计数，且加仓价通常优于首推价，会造出虚假盈利。
   **v0.17.0 起由 `rec_pnl.py` 强制**（`classify()` 按 结算日+腿+方向+档位 只取首次出现的那一行，
   其余标 `↳ 加仓` 仅在明细里可见）——**CSV 里可以照录全部流水，不必人工折叠**。
2. 论点翻转后重新建仓（如 9/11 的 NO32 先押「不是 32」、后押「高于 32」）**仍算同一条腿**。
3. **记录的是建议，不是成交**。实际成交量受订单簿深度限制（薄盘常只能成交建议额的 20–40%），
   所以台账是**收益上限口径**：真金白银的波动小于表内数字，但**符号（胜 / 负）不受影响**。
4. **未结构化留存的日期不硬凑**：9/07–9/08、9/10 在 CSV 里以 `# 未纳入台账` 注明，宁可空着。
5. **口径的副作用：不记加仓 = 不记加仓的亏损。**
   9/12 的 YES31 首推在 10:15（$15），同一腿 13:50 又以 0.010 加仓 **$54** 并全额归零 ——
   $54 不入账，于是当日显示 **+$24.22**；若计入则翻为 **−$29.78**。
   9/15 同向：首推口径 6 腿 **−$334.31**，若把 13 条同腿加仓一并计入则为 **−$709.99**（`--all-legs`）。
   → **当日盈亏的符号对「加仓有没有被记录」高度敏感。** 读表时以**逐腿胜负**为主信号、
   金额只作量级参考；要精确对账必须保留**实际成交流水**（`PNL_actual.md`）。
6. **`outcome=void` 永不入账**（v0.17.0）：作废 / 撤回 / 未发出的建议既不计成本也不计盈亏，
   **也不再被当成「未结算」** —— v0.16.x 把它算成 open，会让该结算日永远收不了口（9/15 实际踩到）。
7. **胜-负按 `outcome` 计，不按盈亏正负**（v0.17.0）：`cost_usd < 0` 的行是**建议卖出**（回收现金），
   其盈亏按空头口径算（卖出价 vs 结算价 1.0），所以会出现「记 ✅ 赢、金额却是小负数」的组合。
8. **平仓 / 减仓建议不单独建腿**（2026-09-16 发现的口径缺口）：第 7 条的负数成本行是为
   「**开仓卖出**」（手上没有多头、直接卖出）设计的。**平掉在册的多头腿**不能这样记 ——
   （a）它与该腿的买入行**同键**（结算日+腿+方向+档位）会被 `classify()` 折叠掉；
   （b）它的经济含义相反（平仓是了结亏损，不是收权利金），按空头口径算会把已实现亏损算成盈利
   （如 9/16 的「卖 29 YES 364 份 @0.020 回收 $7.28」会被记成 **+$7.28**）。
   → 平仓 / 减仓只在 `note` 与 CSV 文件头的「当日流水」里记录；**要跟真实平仓必须用 `PNL_actual.md`**。
9. **同日多轮修正时，入账用「当日首次给出的那一版」**（即 CSV 行序上的首行），
   后续改价 / 换腿作 `↳ 加仓` 折叠，但要照录。
   9/16 实例：09:05 首推 30YES @0.26 / 32NO @0.83，10:01 自我修正改价为 0.30 / 0.81 并新增 31NO、
   11:30 再反手加 32YES —— 入账用 09:05 的两个价。
   代价写在明处：**该口径会让「后来被判定依据失效的那一版」继续承担盈亏**；
   若改用 10:01 修正版，9/16 由 **−$336.90 变为 −$308.31**（差 1.2% 本金）。
   两种都能算，选了就在 CSV 文件头写明。
10. **窗口外的「预案」与「研究留档」照录入账**（2026-09-17 新校准点，**待 Eason 拍板**）：
   9/17 起 SKILL 要求在窗口外披露 edge>8% idea 并附**留档 Kelly**（v0.19.2 / 0.19.3），
   于是当日出现两类非执行腿 —— ① 10:30 前给的「复跑后须按新价重算」预案、② 12:05 起的
   「研究观察 非执行指令」。本次采用**照录 + 每条腿取当日首个带金额版本**（与 9/15 窗口外腿
   一律入账的先例一致，也让「哪个下注时点 edge 最稳」的留档数据真正沉淀进台账）。
   代价写在明处：**9/17 = 5 腿 −$88.94；若只计窗口内可执行腿则 2 腿 −$13.51**（差 $75.43）。
   → 若 Eason 定「留档不入账」，改法是给这些行加 `outcome=void`（脚本会折叠），数字随即可复算。
   **2026-09-20 补强（首次出现「折叠反向放大亏损」）**：当日 13 条流水全量口径 **−$687.11**，
   首推口径 **−$783.97** —— 被折叠的 4 笔盈利加仓（NO32 +$338.28、YES33 +$250.16）**多于**
   4 笔亏损加仓（YES34 −$51.58、NO33 −$440.00），折叠反而使当日多亏 **$96.86**（本金 3.9%）。
   → 所以「首推口径」既不是保守也不是激进，**方向不定**（9/15–9/17 是减亏、9/20 是增亏），
   它只是「同一论点只算一次」的记账规则。同日若**只计窗口内（10:30–12:00）可执行腿 = 2 腿 +$28.20**，
   **与全量 −$687.11、首推 −$783.97 符号完全相反** —— 这是口径 10 应改判「窗口外不入账」的最强论据。
   **2026-09-21 第三个校准点（首次由会话自己收窄，方向与 9/17 / 9/20 相反）**：当日会话日志明写
   ① 00:20 隔夜轮「留档腿标研究观察 非执行指令」且「**10:30–12:00 重跑后才是台账口径**」，
   ② 08:55 轮「标研究观察、**不入台账**」。→ 本次**只入账窗口内那 1 条**（NO32 @0.520 $118），
   00:20 的 3 条（YES31 $146 / YES30 $12 / NO32 $90）与 08:55 的留档**一律不建腿**。
   这意味着**口径 10 在三天里出现了三种做法**（9/17 照录、9/20 照录、9/21 排除），
   **必须先拍板再继续** —— 否则台账的累计值会随「当天有没有人手写一句不入台账」而漂移。
   本次选择服从会话明写的排除声明（因为自动化只能读到结构化流水，读不到未写下来的意图），
   并已在 CSV 文件头逐条列出被排除的 4 条留档，**补 4 行即可复算**。
11. **「零腿结算日照实留空」**（2026-09-18 立规，**09-19 第二次、09-26 第三次适用**）：某结算日若没有任何可信来源
   能还原当日建议流水，**不得用 `--watch` 的概率自造 Kelly 腿、也不得事后补录**；只做两件事 ——
   ① 在 CSV 文件头登记该日结算档与空缺原因；② 跑一次
   `rec_pnl.py --settle <日>=<档> --status provisional`（无腿时打印「回填 0 条记录」，**这不是失败**）。
   `PNL.md` 由脚本**按腿汇总**，不会出现该日行；累计里的「N 个结算日」只数有腿的日。
   判定「零腿」的四条硬证据（**其中三条齐即可下结论**）：
   - **A. 推荐引擎跑没跑**：`scripts/data/decision_log.csv` 有没有**写入时间戳（第 1 列）**为当日的行。
     ⚠ **不要用 `target_date`（第 2 列）判** —— 该文件会提前写入**未来市场**的快照
     （如 09-15 11:01 写的行 target_date 已排到 09-21），`grep <日期>` 会得到 6 条**假阳性**。
     文件最后写入时点距今 ≥1 天 = 引擎当日未运行。
     ⚠ **A 只是「必要」，不是「充分」**（09-26 实测）：`--watch` 每天都会跑，但**从不写 `decision_log.csv`**
     → 当日可能「引擎没跑、watch 跑了、会话仍出腿」（09-25 即此形态：09-24 之后 decision_log 停写，
     但 17:00 会话出了 2 条腿）。故 **A 命中时仍须做 B / C / D**，尤其是 B（当日会话日志）。
   - **B. 当日会话日志**：`WorkBuddy/*/.workbuddy/memory/YYYY-MM-DD.md` 是否存在
     （注意本自动化的记忆文件落在同目录，要看清是「由自动化写入」还是真实会话流水）。
   - **C. 会话检索**：`conversation_search` 对当日返回 0 条。
   - **D. `watch.log`**：只有实况 + 概率，**无 Kelly / 建议仓位段**（watch 模式从不输出仓位）。
   边界未验证：若零腿日的**次日** Eason 补发当日流水，「不得事后补腿」与「照实留空」会冲突
   → 需拍板；若补录，必须在 `note` 里写明补录时点。
12. **窗口内（10:30–12:00）的建议腿一律入账，不以「用户是否确认成交」为前提**（2026-09-25 立规）：
   台账文件头自始即写明「记录的是**建议**的结算盈亏，不是实际成交记录……成交与否未知」，
   故「未确认成交」**不构成排除理由**。9/25 当日会话把 11:53:50 的窗口内腿写成 `#` 注释行
   （理由「用户未确认成交」），本自动化按 09-15 / 16 / 17 / 20 / 21 / 22 / 23 的一致做法**补建 2 行**：
   YES31 @0.050 × 29 份 = $1.45（结算 32 → 输 −$1.45）、NO33 @0.700 × 53 份 = $37.10（结算 32 → 赢 +$15.90）
   → 当日 **+$14.45（+37.5%）**。
   → 判据是**腿在不在窗口内 + 流水是否结构化（价 / 份数 / 金额 / 时刻齐全）**，不是「有没有成交回执」。
   ⚠ 仅当 Eason 明确判定「未确认成交即不建腿」时才改 —— 改法是给对应行加 `outcome=void`，数字随即可复算。
   ⚠ 与之互补：**窗口外（含 D-1）腿仍按口径 10 处理**（照录 / 排除，待拍板），两者不要混淆。
   ⚠ **运维陷阱（本次实测）**：`#` 注释行**只能写在文件头的注释块里**。`rec_pnl.py::_header_lines()`
   只保留「第一个非注释行之前」的注释，**追加在文件末尾的注释行会在下一次 `--settle --write` 时被静默丢弃**
   （9/25 会话写在尾部的 `#2026-09-25,COMBO,...` 即属此列）。新增的口径 / 流水说明必须插在字段头
   `settle_date,...` **之前**。

**工具**
```bash
py -3 scripts/rec_pnl.py                                   # 逐日汇总 + 总计 + 累计曲线 + 按方向拆分
py -3 scripts/rec_pnl.py --open                            # 只列未结算的腿
py -3 scripts/rec_pnl.py --all-legs                        # 不折叠同腿加仓（看全量建议流水）
py -3 scripts/rec_pnl.py --settle 2026-09-12=33 --write    # 回填结算档（近期日唯一可靠途径）
py -3 scripts/rec_pnl.py --settle 2026-09-15=31 --status provisional --write   # 官方源未出时
py -3 scripts/rec_pnl.py --auto --write                    # 用 maxt_HKO.csv 回填
py -3 scripts/rec_pnl.py --markdown                        # 重新生成仓库根目录 PNL.md
```
`--settle` 默认**只试算不落盘**，加 `--write` 才写回 CSV；`--status` 决定写入的
`settle_status`（默认 `confirmed`，官方源未出时用 `provisional`，**不必再手工改回**）。

⚠ **CSV 的 `note` 字段禁止出现半角逗号，也不要改列分隔（2026-09-13 首次实测；2026-09-21 再次踩中）**

`rec_pnl_log.csv` 是逗号分隔文件，`note` 里写 `[28.6,29.0)` 会直接撑出多余列。

note 被截到「峰值 ∉ [32」，随后 `--settle --write` 立刻把它固化。**修复方式 = 整行重写并复查列数。**
- 区间一律用 **en dash 或波浪号**：`28.6–29.0`、`28.6~29.0`。**不要用半角逗号**。
